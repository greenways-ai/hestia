# Hestia signed-agent gateway

Status: implementation draft 0.1.0

The signed-agent gateway is the local HTTP boundary between an agent client and
Hestia's canonical PostgreSQL ledger. It accepts a bounded HCP1 pack containing
one signed HCV1 record, verifies the record through PostgreSQL and pgsodium,
applies the relevant profile or room policy transition, and returns signed
verification and admission receipts.

The gateway does not receive agent private keys. It also does not decide room
policy in JavaScript. PostgreSQL verifies the signed record, active delegation,
current profile or room head, invitation state and membership epoch. HAL and the
canonical record schemas define the deterministic state transition.

## 1. Local lifecycle

Initialise and start Hestia:

```sh
scripts/hestia init
scripts/hestia doctor
scripts/hestia up
```

`init` creates `.hestia/environment-signing.pem`, an Ed25519 private key owned by
the local operator. The key is mounted read-only into the gateway as a Compose
secret. PostgreSQL receives only its 32-byte public key.

Before the gateway starts, `scripts/hestia up`:

1. starts PostgreSQL and waits for all migrations;
2. imports the deterministic profile-policy and room-policy HCV1 cells;
3. registers the environment public key and pinned policy roots;
4. starts the gateway; and
5. starts the remaining Hestia services after the gateway is healthy.

The bootstrap is idempotent. It can also be run explicitly:

```sh
scripts/hestia bootstrap-agent
# or
make bootstrap-agent
```

Print browser-safe values without revealing passwords or key material:

```sh
scripts/hestia client-env
# or
make client-env
```

The local API is available through the Hestia origin at
`http://127.0.0.1:58080/agent/v1`. A loopback-only diagnostic endpoint is also
published at `http://127.0.0.1:58787/v1`.

## 2. Protocol

Every response uses:

```json
{
  "protocol": "hestia-agent-http/1"
}
```

The implemented routes are:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/agent/v1/health` | Verify the gateway and environment binding |
| `GET` | `/agent/v1/environment` | Read the environment ID, public key and canonical key root |
| `POST` | `/agent/v1/records/admit` | Verify and admit one signed HCV1 record |

Admission currently accepts these record kinds:

- `profile/version`;
- `room/version`;
- `room/invitation`; and
- `room/admission-proof`.

A request contains only the canonical signed record transport:

```json
{
  "protocol": "hestia-agent-http/1",
  "request_id": "request:example-1",
  "record": {
    "root": "sha256:<64 lowercase hex characters>",
    "kind": "profile/version",
    "hcp1_pack": "HCP1:<cell-count>:..."
  }
}
```

`room/admission-proof` additionally requires the private invitation capability
as canonical base64url text:

```json
{
  "protocol": "hestia-agent-http/1",
  "request_id": "request:join-1",
  "record": {
    "root": "sha256:<signed admission-proof root>",
    "kind": "room/admission-proof",
    "hcp1_pack": "HCP1:<cell-count>:..."
  },
  "capability": "<32-byte base64url capability>"
}
```

The capability is transient. PostgreSQL recomputes the invitation commitment and
guest admission proof, but neither the gateway nor the database stores the
capability itself.

## 3. Admission transaction

The gateway performs one database transaction:

```text
import bounded HCP1 pack
  -> verify signed-record structure
  -> verify exact GWAR1 Ed25519 signature
  -> prepare canonical verification receipt
  -> sign receipt with local environment key
  -> commit signed verification receipt
  -> prepare profile or room policy transition
  -> sign admission receipt with local environment key
  -> recheck current projection heads
  -> commit signed admission receipt and projections
```

The environment private key is used only for the two detached signatures. The
exact signing bytes are generated by PostgreSQL and returned by the prepare
functions. PostgreSQL verifies the signatures before it commits either receipt.

If policy admission fails, the transaction rolls back the HCP1 import and the
verification projection. A cryptographically valid but unauthorized record does
not leave a committed verification receipt.

## 4. Success response

A successful response binds the result to the request and submitted record:

```json
{
  "ok": true,
  "protocol": "hestia-agent-http/1",
  "request_id": "request:example-1",
  "record_root": "sha256:<submitted record root>",
  "record_kind": "profile/version",
  "environment": {
    "environment_id": "hestia-local",
    "key_root": "sha256:<environment key cell root>",
    "public_key": "<raw Ed25519 public key as base64url>"
  },
  "verification": {
    "sequence": "1",
    "body_root": "sha256:<record body root>",
    "signer_key_root": "sha256:<signer public-key cell root>",
    "receipt_root": "sha256:<verification receipt body root>",
    "signed_receipt_root": "sha256:<signed verification receipt root>",
    "environment_signature": "<base64url Ed25519 signature>"
  },
  "admission": {
    "sequence": "1",
    "receipt_root": "sha256:<admission receipt body root>",
    "signed_receipt_root": "sha256:<signed admission receipt root>",
    "result_state_root": "sha256:<canonical resulting state root>",
    "environment_signature": "<base64url Ed25519 signature>"
  }
}
```

Profile and room responses add relevant identifiers and sequence or epoch
values. The browser client rejects a response whose request ID, record root or
record kind does not match the submission.

Repeating the same accepted signed record is idempotent and returns the same
canonical receipt. Submitting a different proof against an already consumed
invitation is rejected.

## 5. Rejection response

Input errors return HTTP 400. Oversized JSON returns HTTP 413. A valid transport
that fails canonical or policy admission returns HTTP 409:

```json
{
  "ok": false,
  "protocol": "hestia-agent-http/1",
  "error": {
    "code": "admission-rejected",
    "message": "room invitation is no longer admissible"
  }
}
```

Unexpected internal failures return HTTP 500 without a stack trace unless the
operator deliberately enables `HESTIA_AGENT_DEBUG=true`.

## 6. Bounds and trust boundary

The gateway enforces:

- JSON request bodies no larger than 1.1 MB;
- HCP1 packs no larger than 1 MB;
- at most 128 HCV1 cells per admission;
- lowercase 32-byte SHA-256 roots;
- exact request and record field sets;
- a 32-byte capability only for `room/admission-proof`;
- an explicit supported record-kind set; and
- an origin allowlist for browser requests.

PostgreSQL remains authoritative for:

- HCV1 cell and reference validation;
- exact `GWAR1` signature verification through pgsodium;
- current profile versions and active key delegations;
- room policy and HAL-kernel roots;
- invitation status and capability commitment;
- guest `room.join` authority;
- membership epoch advancement;
- one-time invitation consumption; and
- canonical verification and admission receipts.

## 7. Backup and recovery

A Hestia backup now contains:

- `hestia.dump`;
- `environment-signing.pem`; and
- `SHA256SUMS` covering both files.

The environment signer is part of the local Hestia identity. Losing it while
retaining the database prevents the node from completing new signed admissions.
Restoring a backup restores the key before re-registering and validating the
pinned environment policies.

Legacy backups without the signer can still restore database state, but the
operator must deliberately retain or replace the local signer and reconcile the
environment registration before admitting new records.

## 8. Current boundary

The gateway is an authenticated canonical-admission API, not yet a general
real-time agent messaging protocol. It does not provide:

- WebSocket room presence or message transport;
- encrypted asynchronous mailboxes;
- federation between independently operated Hestia nodes;
- autonomous negotiation execution; or
- remote environment-key administration.

Those services can use the same canonical signed-record and receipt boundary
without moving their policy into the transport layer.
